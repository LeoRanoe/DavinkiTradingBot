# Building your own strategy

This is the end-to-end story: what you can build, how it's validated, how
it's versioned, and exactly what it can and can't do. For the underlying
architecture, see `docs/architecture/strategy-platform.md`; for the
built-in strategies, see `docs/strategies/README.md`.

## 1. The DSL - declarative, never code

A custom strategy is a `DslDefinition`: plain JSON data describing which
timeframe(s) and side(s) to trade, an entry condition tree, and a stop/
target formula. There is no code execution involved anywhere - the DSL is
interpreted directly by `lib/strategy-platform/dsl/evaluate.ts`, a plain
recursive function over the typed tree. No `eval()`, no `new Function()`,
no VM, no generated JavaScript, ever
(`lib/strategy-platform/dsl/no-arbitrary-code.test.ts` makes this a
checked regression, not just a claim).

### Condition primitives available today

`ALL` / `ANY` / `NOT` (combinators), `COMPARE`, `CROSS_ABOVE` /
`CROSS_BELOW`, `SESSION`, `PERCENT_CHANGE`, `BULLISH_CANDLE` /
`BEARISH_CANDLE`, `CANDLE_PATTERN` (engulfing/hammer/shooting star), `BOS`
(break of structure), `LIQUIDITY_SWEEP`, `FVG` (fair value gap). Value
primitives: `PRICE`, `CONST`, `EMA`, `SMA`, `RSI`, `ATR`, `VOLUME`,
`HIGHEST`, `LOWEST`, `SWING_HIGH`, `SWING_LOW`. The structure primitives
(`BOS`/`LIQUIDITY_SWEEP`/`FVG`/`SWING_HIGH`/`SWING_LOW`/`CANDLE_PATTERN`)
are the exact same functions JeanFX's own state machine uses
(`lib/strategy/jeanfx-v1/primitives/`) - not a separate, weaker
reimplementation.

A primitive that isn't listed above and isn't yet implemented (`MSS`,
`OHLC`) is rejected with a distinct "recognized but not yet implemented"
error - never silently ignored, never treated as a no-op.

### Stop and target

Stop: `FIXED_PERCENT`, `ATR_MULTIPLE`, `BELOW_SWING`/`ABOVE_SWING`,
`BELOW_SIGNAL_LOW`/`ABOVE_SIGNAL_HIGH` (the `BELOW_*` kinds only valid for
LONG, `ABOVE_*` only for SHORT - checked at validation time). Target:
`R_MULTIPLE`, `FIXED_PERCENT`, `NEXT_SWING`, `NEXT_LIQUIDITY_POOL`.

### Safety limits

Max rule nesting depth (6), max total rule count (60), max indicator
lookback (500 bars), max timeframes per strategy (3), max instruments per
configuration (25). A definition exceeding any limit is rejected before it
is ever saved.

## 2. Building one

Visit **Strategies → Create Strategy** (`/strategies/new`). The visual
rule builder operates on the real rule tree - no manual JSON is required,
though you can view/export the exact JSON that will be saved at any time.
As you build, you see a live plain-English summary (e.g. *"Trades LONG on
the H1 chart when: all of: the 20-period EMA crosses above the 50-period
EMA; RSI(14) is above 55. Stop: below the most recent swing low, with a
0.20% buffer. Target: 3R (3x the stop distance)."*) generated by
`lib/strategy-platform/dsl/describe.ts` - never a separate, potentially-
inconsistent hand-written description.

You can start from a template (EMA Trend, RSI Pullback, Breakout) and
customize it, or start from scratch.

## 3. AI assistance (a hook, not a live feature in this build)

`lib/strategy-platform/ai-assistant.ts` defines the contract an AI
assistant would use if/when one is wired up: you describe what you want in
plain language, the assistant proposes a `DslDefinition`, the system
validates it through the exact same validator a hand-built strategy goes
through, the UI previews it, and **you** explicitly save it. An AI
proposal is always `DRAFT` and is never auto-saved, never auto-activated,
and can never touch PAPER/LIVE authorization, an existing version's rules,
or the deterministic risk engine - see the module's `AI_ASSISTANT_BOUNDARY`
constant for the full allowed/forbidden list. No LLM provider is called by
this contract today; it exists so that whenever one is connected, it has
exactly one narrow, validated door in.

## 4. Versioning

Saving creates version 1. Every subsequent edit creates a NEW version
(version 2, 3, ...) - a version's rules are immutable once created,
enforced by a database trigger independent of the application code. Your
existing configurations keep pointing at the version they were created
against; nothing is silently migrated. If you want a configuration to use
your new rules, you explicitly point it at the new version.

## 5. Configuring and assigning

A **StrategyConfiguration** is how you want to run a specific version:
name, parameters, which instruments. A **StrategyAssignment** is the
explicit "this actually runs" switch: mode, instrument list, priority,
enabled/disabled. Nothing runs just because you created a strategy or a
configuration - you must explicitly assign it.

New assignments always start in `RESEARCH` mode. From
**Settings → Strategies** you can switch an assignment between `RESEARCH`
and `SHADOW` freely. `PAPER` requires the account owner to explicitly
authorize that specific assignment - there is no self-service path, by
design (a database trigger refuses to set the authorization column from
any route except an owner-authenticated one). `LIVE` has no path to
activation anywhere in this codebase - not from the UI, not from the API,
not from the database - regardless of role.

## 6. Backtesting

**Backtests** run your strategy (compiled from your DSL into a real
`StrategyContract`, exactly like any built-in) through the identical
generic backtest engine JeanFX uses
(`lib/strategy-platform/backtest.ts`) - there is no separate, weaker
simulator for custom strategies. Results always carry evidence-quality
warnings when applicable (too few trades, short history, high parameter
count, in-sample only, zero-cost assumption) and never claim "profitable
strategy" from one run.

## 7. Promotion path (workflow, not automatic)

```
DRAFT -> BACKTESTED -> SHADOW -> PAPER -> LIVE
```

These are workflow concepts, not automatic transitions. A positive
backtest, a high win rate, or an AI recommendation never by itself moves a
strategy forward - PAPER requires explicit owner authorization (see
above), and LIVE requires infrastructure this build does not have at all.

## 8. What you can't do

- Edit a built-in strategy's source, or have an import overwrite a
  built-in's slug.
- See another user's private (non-`PUBLIC`) custom strategy, its versions,
  its configurations, or its backtests - enforced by database row-level
  security, audited in Prompt 3 (see `docs/architecture/strategy-platform.md`
  section 14 "RLS audit findings").
- Submit executable code of any kind - the DSL has no code-execution
  surface to submit it through.
- Reach PAPER or LIVE by editing a request payload, importing a crafted
  file, or any other client-side trick - mode authorization is resolved
  entirely server-side, and the less-permissive of "what you asked for"
  and "what you're authorized for" always wins
  (`resolveEffectiveMode()`).
